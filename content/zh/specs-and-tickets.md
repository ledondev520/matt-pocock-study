## 聊天里的决定，下一次还能找到吗？

昨天确认了保存失败时保留输入，今天换了会话，agent 却把表单清空。决定留在长聊天里，没有变成可查的实施依据；另一种问题是规格太长，旧细节盖住了真正工作。

规格要解决的是决定如何传递。它应让新会话知道什么已定、什么没定，以及完成时要拿出什么证据，而不是增加另一份容易失效的说明。

## 只写已经确认的行为

把目标、行为、范围外事项和验收方式写清楚。对于尚未决定的同步策略，直接标为待确认；不能为了让文档完整，就把自己的猜测写成需求。

```cards
- **目标与行为** 谁要完成什么，系统怎样回应？
- **边界与未知** 这次不做什么，哪些问题仍需决定？
- **验收方式** 哪些操作和结果能够证明行为成立？
```

## 工单先贯穿一条完整路径

`/to-spec` 收拢已定决策，`/to-tickets` 再切成小而完整的纵向能力。第一张先连接输入、处理与输出，验证路径接得上，再逐步扩展。

这条细小的端到端实现常叫 tracer bullet。它并非 Matt 原创术语；重点是尽早得到系统能否协作的反馈，而非先把每一层分别写满。

## 给材料安排不同的寿命

Matt 的实践倾向把工单放在 tracker，规格用后清理，长期决定放进 ADR。需要审计、协作或追溯的团队，应先约定归档政策，不能把个人习惯写成统一删除要求。

<!-- compare -->
| 材料 | 保存什么 | 何时处理 |
|---|---|---|
| 规格 | 已定目标、行为、边界、验收 | 实施后按团队政策清理或归档 |
| 工单 | 一个小闭环、依赖、证据 | 跟随交付，留在追踪器 |
| ADR | 长期决定及其理由 | 长期保留，变化时注明替代关系 |

## 练习：收藏功能先交哪一片？

先预测「前端做完、接口做完、存储做完」能否分别证明收藏可用。再只选一条内容，写一张从点击到持久保存的小工单。

```exercise
title: 让一条内容的收藏可验收
- 任务：点击收藏并保存，刷新后仍显示已收藏。
- 依赖：内容 ID、现有用户身份、可用的存储接口。
- 范围外：批量收藏、筛选和多端同步。
- 失败时观察到：保存失败有提示，不能显示假成功，并允许重试。
- 成功时观察到：点击、保存、刷新后，状态与存储一致。
- 验收证据：记录一次成功操作和一次模拟保存失败的结果。
answer: 这张工单覆盖输入、处理与输出，能独立演示。若接口尚不存在，先明确前置依赖或把最小接口纳入闭环，不能留一个无法验收的空壳。
```

```note
kind: inference
本站建议：把下一张工单留给取消收藏，先证明一个方向的状态能正确保存。具体切分仍应由已有依赖与风险决定。
```

## 怎样才算完成？

交出一张能独立验收的工单，列明依赖、失败与成功观察、证据位置。读者无需回看聊天就能执行它；未确认事项不能悄悄变成实施前提。

带着这张工单进入[实现与反馈](/zh/implementation-and-feedback)，实际跑出验收结果。

## 速查

```cards
- **规格存决定** 已定与未定分开，验收写具体。
- **工单交能力** 先贯穿输入、处理、输出。
- **长期留理由** ADR 与临时材料分别管理。
```
